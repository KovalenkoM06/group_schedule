# Лабораторна робота №3 — Розклад занять групи (Варіант 4)

Проєкт з дисципліни «Програмування мовою Dart» (варіант 4, номер у списку збірної групи — 19: `19 % 15 = 4`).
Предметна область: **Розклад занять групи** (`дисципліна, викладач, тип, день тижня, час початку, аудиторія`, а також числові поля тривалості заняття у хвилинах та оцінки/рейтингу курсу).

## Структура програми

Проєкт розвивається послідовно від лабораторної роботи №1 до лабораторної роботи №3:
- `lib/group_schedule.dart` — містить предметну ООП-модель (`Lesson`, `DayOfWeek`, `LessonActivity`, `RoomValidationMixin`, синхронне сховище `Repository<T>`), а також асинхронний шар із ЛР №3: `AsyncRepository<T extends Identifiable>`, функції порівняння послідовного та одночасного виконання `Future`, обробку групових помилок (`Future.wait` і `.wait` з `ParallelWaitError`), потоковий генератор `async*` (`watchAll`), подію `ScheduleEvent`, буферизований `StreamController`, конвеєр трансформації потоку (`where -> map -> take`) та обчислення у фоновому ізоляті через `Isolate.run`.
- `bin/group_schedule.dart` — асинхронна точка входу `Future<void> main()`, яка послідовно демонструє всі 10 експериментів лабораторної роботи №3.
- `test/group_schedule_test.dart` — набір із 8 модульних тестів (`package:test`) для перевірки асинхронних операцій `AsyncRepository`, помилок та порядку подій потоку.

## Прийняті рішення та вибір типів даних

1. **Усунення зауважень до попередньої роботи:**
   - У класі `Lesson` прибрано подвійний розбір CSV-рядка: метод `_parseCsvFields` виконує розбір один раз і повертає типізований запис `_ParsedLessonFields`, який напряму передається в конструктор `Lesson._fromParts` без мертвих запасних значень `??`.
   - Додано сувору перевірку переповнення дат після `DateTime.tryParse`: розібрана дата форматується назад у ISO-рядок через `toIsoSecondsString()` і порівнюється з вхідним текстом, щоб некоректні дати на кшталт `2026-13-45` не переносилися автоматично на наступний рік.
   - У документаційних коментарях `///` до `operator ==` та `hashCode` явно зафіксовано, чому приватне поле `_notes` свідомо не бере участі у порівнянні слотів розкладу.
2. **Асинхронне сховище (`AsyncRepository<T extends Identifiable>`) та `Future`:**
   - Операції `save`, `saveAll`, `load`, `loadAll` і `delete` повертають `Future` з імітацією затримки звернення до зовнішнього джерела через `Future<void>.delayed`.
   - В `analysis_options.yaml` увімкнено правила `unawaited_futures` та `discarded_futures`, щоб аналізатор підсвічував випадково пропущений `await`.
   - Порівняння трьох операцій по 500 мс через `Stopwatch` показує різницю між послідовними `await` (~1530 мс) та одночасним очікуванням через `Future.wait` (~510 мс). Для групових помилок порівняно класичний `Future.wait` (втрачає успішні результати при першому збої) та розширення `.wait` на списку `Future` (кидає `ParallelWaitError`, зберігаючи і успішні результати в `e.values`, і помилки в `e.errors`).
3. **Потоки даних (`Stream`, `async*`, `StreamController`):**
   - Метод `watchAll` реалізовано генератором `async*`. Доведено його лінивість: код на початку тіла генератора не виконується до моменту підписки (`await for` або `listen`).
   - Для демонстрації помилки всередині потоку використано `yield* Stream<T>.error(...)`, щоб генератор міг продовжити видачу наступних елементів для слухачів із `cancelOnError: false`.
   - Кожна підписка через `listen()` зберігає об'єкт `StreamSubscription` і обов'язково скасовує його через `await subscription.cancel()` у блоці `finally`.
4. **Паралельні обчислення (`Isolate.run`):**
   - Важке синхронне обчислення контрольної суми розкладу (`computeScheduleHeavyDigest`) винесено в `Isolate.run`. Експеримент зі зміною глобальної змінної `globalIsolateProbe` всередині `Isolate.run` підтвердив повну ізоляцію куп пам'яті між головним і робочим ізолятами.

## Обґрунтування щодо `!`, `late` та `dynamic`

У коді всього проєкту (`lib/`, `bin/` та `test/`) **не використано жодного оператора `!`, ключового слова `late` або типу `dynamic`**:
- Навіть у модульних тестах (`test/group_schedule_test.dart`) змінні `repository` та `sampleLessons` ініціалізуються безпечними початковими значеннями при оголошенні та оновлюються в `setUp(...)`, що дозволило повністю обійтися без ключового слова `late`.
- Усі перевірки на `null` виконуються через промоцію типів локальних `final`-змінних, приватного `final`-поля `_notes` або безпечні оператори `?.` та `??`.

## Використані пакети з `pub.dev`

Зовнішні бібліотеки в розділі `dependencies` не підключалися — асинхронність, потоки та ізоляти реалізовані стандартними бібліотеками SDK (`dart:core`, `dart:async`, `dart:isolate`).

У розділі `dev_dependencies` підключено два офіційні пакети:
- **`lints` (`^6.0.0`)** — офіційний набір правил статичного аналізатора від команди Dart (`package:lints/recommended.yaml`) для перевірки коду командою `dart analyze`. Як альтернатива розглядався пакет `very_good_analysis`, але `lints` є стандартним рекомендованим пакетом у методичних вказівках.
- **`test` (`^1.25.0`)** — стандартний фреймворк модульного тестування Dart для запуску тестів командою `dart test` (надає `group`, `test`, `setUp`, `expect`, `expectLater`, матчери `completion`, `throwsA`, `emitsInOrder`, `emitsError`). Як альтернатива розглядалися ручні перевірки через `assert` у `bin/`, але вони не підтримують асинхронні матчери потоків та ізольований запуск тестів. Пакет розміщено саме в `dev_dependencies`, тому що тести потрібні лише під час розробки й перевірки коду і не повинні потрапляти у фінальну збірку програми чи тягнути тестові залежності для споживачів бібліотеки.
